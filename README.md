# ReLU.chat

Six free learning assistants that retrieve and explain curated knowledge in your browser. Chat questions are processed locally. Hosting, the neural matching model download, external links, and separate signup or purchase flows still use the network.

There are also six interactive ML tools, 82 learning guides and a crawlable page for every assistant topic under `/learn/`. The assistants can misunderstand questions. They assemble curated fragments, do not execute code, and cannot solve arbitrary exercises.

## Runtime

The shared vanilla JavaScript engine starts with keyword matching, explicit entity/intent cues, and field-weighted BM25. A 13,079-parameter policy advises response intent and depth using verified WebAssembly or JavaScript. Built-in rules keep chat usable if policy assets are unavailable. Complete answers include math and available source links, with topic follow-ups, reset, and text export. Shared conversational handling understands casual greetings, thanks, acknowledgments, and stretched words such as “howww.” A greeting before a real question does not hide the question. These small turns do not require model inference.

### Inference layer

`core/responder.js` runs before rendering, in the browser and in the Node tests alike. It is deterministic and adds no download:

- `core/query-analysis.js`: a finite-state cascade splits a message into up to three questions, labels each (definition, example, formula, use, comparison, relation, why, how, who, when, where, how many, yes/no, condition), extracts the asked-about phrase, finds pronouns and ellipsis, and recognises requests for live data, calculations, code, opinions or actions.
- `core/discourse.js`: a discrete Bayes filter (hidden-Markov forward step) over topics, salience-based pronoun resolution with person/concept agreement and bridging (“its memory”), and a scalar Kalman filter for preferred answer length.
- `core/lexicon.js`: accent-folding tokenizer, conservative stemmer, math-aware sentence splitter, entry-level IDF, and a symmetric-delete spelling index.
- `core/grounding.js`: typo-tolerant alias linking, information-weighted evidence accounting, coordination-aware grounding, and the knowledge boundary: answer, closest match, quoted mention, another assistant (`data/topic-directory.json`, generated by the site build), or “I don't have notes on X”. That last reply needs specific evidence, such as an unknown word in a short concept question, a two-word term the notes never use, or an unknown modifier of a known topic. Topics asked by name are never refused.
- `core/answer-planner.js`: answer-first extraction for who/when/where/how-many/yes-no/why questions, which states when the notes lack the answer, and beam (Viterbi-style) decoding over curated fragments with discourse-coherence transitions, TextRank centrality and novelty penalties.

With neural matching loaded, MiniLM similarity is a further evidence channel. A description that words alone cannot place, but whose similarity to one topic is at least 0.55 with a margin, is answered as the closest match. Unknown names, new terms and concept questions with unknown words still veto it. On the development and casual-chat sets, that threshold matched 54% of covered-topic questions and 1.9% of the others. Passage-level matching (best fragment per topic) was measured and rejected: it raised wrong-topic matches from 0.5% to 8.1% at equal strictness. `dev/eval/neural.html` runs all three evaluation sets in a browser with the model loaded.

Thresholds live in `data/boundary-calibration.json`, produced by split-conformal calibration on questions generated from each knowledge base (`node dev/scripts/calibrate-boundary.mjs --write`). Calibration never makes an assistant stricter than the defaults. The previous pipeline remains as an automatic fallback.

Neural matching is on by default. When a chat opens, the engine loads the approximately 22 MB quantized MiniLM sentence-embedding model plus Transformers.js runtime files in the background. Questions asked meanwhile are answered by the policy network and lexical retrieval. The complete knowledge/intent embedding set is prepared before switching backends, between answers; incompatible query vectors are cleared. Public knowledge embeddings are cached by content hash in IndexedDB, and the service worker keeps the model bytes, so later visits start quickly. If the model cannot load, the status shows “fast matching” and a retry button. Conversations remain in memory unless exported.

## Develop and verify

Use Node.js 22.13 or newer and Python 3.11 or newer locally. `npm run dev` serves the site at http://127.0.0.1:8017. No npm dependency installation is needed. PHP endpoints require a PHP-capable server. Production uses HTTPS and the Apache rules in `.htaccess`.

```bash
npm test
```

This runs every unit suite, six-bot conversation checks, the dialogue regression bar (no covered topic may be refused), committed model/WASM parity fixtures, deployment safety tests, blog validation, and the static site audit. Results go to ignored `dev/exports/`. GitHub Actions runs the same command on pushes and pull requests with a ten-minute job timeout. It does not install PyTorch, run nightly training, or publish models.

## Dialogue evaluation

`node dev/scripts/eval-dialogue.mjs --compare` scores the current layer and the previous pipeline on `dev/datasets/dialogue-eval`. Add `--set dialogue-test` or `--set dialogue-final` for the other question sets, `--verbose` for failures, and `--write data/dialogue-evaluation.json` to publish. The sets were written by separate models from topic lists. `dialogue-eval` guided development. `dialogue-test` was first run blind and then used to diagnose general failure causes. `dialogue-final` was written after the layer was frozen and scored once. The figures measure routing, honesty about coverage and reference resolution, not the factual accuracy of the curated text.

## Fast laptop policy training

Install the CPU training dependency with `python3 -m pip install -r dev/requirements-fast.txt` in your preferred virtual environment. Clang with wasm-ld is needed to rebuild WASM. No PyTorch, GPU, or remote training service is needed. The whole workflow can be bounded below the ten-minute allowance:

```bash
# This outer deadline covers dataset generation, training, and verification.
timeout 580s bash -e -c '
  node dev/scripts/build-policy-dataset.mjs
  python3 dev/scripts/train-policy-fast.py --max-seconds 120
  bash dev/scripts/build-policy-wasm.sh
  node dev/scripts/verify-fast-policy.mjs
'
```

Training has a supervised warm-up followed by fresh on-policy contextual-bandit REINFORCE updates, a reward baseline, and an entropy bonus. Reward measures agreement with authored routing labels; it does not measure factuality or user satisfaction. The export matches the runtime architecture without LayerNorm, and folds training feature scaling into the first layer. Training accepts at most 540 seconds and exports candidates under `dev/exports/fast-policy/`; it does not automatically publish weights. `verify-fast-policy.mjs` verifies that candidate, rather than silently evaluating deployed weights.

The September 9 release used 2,688 authored cases, split into 1,830 train, 420 validation, and 438 test cases. Topics are disjoint across splits; training templates differ from validation/test templates. The final run took 3.10 seconds. Joint test mode/intent accuracy was 93.6% for the old policy and 98.6% for both the supervised and RL checkpoints. No additional RL test gain was measured. Two development training runs took 6.33 seconds in total.

Before promotion, inspect the validation gate, compare against the prior model, check Python/JS/WASM parity, and run chat regressions. Publish matching model bytes and SHA-256 manifests together. The public report at `data/policy-evaluation.json` includes the scope and measurements. Learned action heads do not replace retrieval, and these figures do not establish general chatbot accuracy.

## Site generation (SEO and shared design)

`node scripts/build-site.mjs` (or `npm run build`) keeps every generated part of the site in sync. `npm test` runs it with `--check`, so CI fails if anything is stale:

- `/learn/` topic pages, subject hubs and the index, generated from `data/bot-packs/*` (math pre-rendered with KaTeX). Add a topic to a knowledge base and it gets a page, internal links, JSON-LD and a sitemap entry on the next build. Topics under 70 words stay `noindex` until they grow.
- The shared shell (head assets, navigation, footer, theme toggle) applied to every static page, with content-hashed asset URLs so deploys never serve stale CSS.
- `sitemap.xml` (`lastmod` only advances when a page's main content changes), `llms.txt`, the topic index in `llms-full.txt`, and the homepage counts, assistant list, tool list and latest guides.
- Error pages, and the book cards (`scripts/site/book.mjs`).

Social images in `assets/og/` are rendered with `npm run build:og` (needs Chrome) and committed. After a deploy that changes the sitemap, `.github/workflows/indexnow.yml` waits for production to serve it and submits only the new or changed URLs to IndexNow. The `blog` generator (`scripts/blog/generate.js`) finishes by running this build.

Design tokens (ink and paper themes, one vermilion accent) live in `assets/shared-design.css`; the type pairing is self-hosted Bricolage Grotesque and Atkinson Hyperlegible Next, with the system monospace stack for instrument labels.

## Learning instruments

`scripts/site/instruments.cjs` builds original subject instruments and content-aware guide motifs as native SVG. `scripts/site/figures.cjs` supplies the interactive ReLU plot, answer pipeline and mathematical tool previews. Guide covers regenerate with the site build and use content-hashed URLs; article bodies remain hand edited.

`assets/js/figures.js` plays one finite Web Animations sequence when a figure is at least 15% visible. It pauses offscreen, on hidden pages and through the navigation's pause control; reduced-motion preferences leave complete static figures. Replay controls appear only when the script loads. No animation dependency or decorative render loop is required. Mathematical invariants and motion lifecycle regressions are covered by `tests/test-illustrations.mjs` and `tests/test-figure-motion.mjs`. Visual direction and browser verification are recorded in `dev/audits/illustration-direction.md`.

## Content

Author blog posts in `content/blog/posts/`. `dev/scripts/build-release-content.cjs` adds the September release posts and updates discovery while preserving hand-edited article pages. `scripts/blog/generate.js` is the full regeneration path; use it only when intentionally replacing generated HTML. `dev/scripts/build-catalog.mjs` derives bot navigation from `data/manifest.json`. `dev/scripts/export-bot-pack.js` builds packs with real fragments and references browser-generated embeddings rather than placeholder vectors.

## Commit-based production deployment

`dev/scripts/release_files.py` defines the shared public-file allowlist. `package-release.py` reads a specific Git commit, not the dirty working tree. `deploy-reviewed-release.py` verifies hashes, backs up changed files outside the web root, replaces them atomically, verifies every public file, and records the source commit. It never deletes production files or deploys databases, uploads, secrets, development tools, or test results.

```bash
python3 dev/scripts/package-release.py --commit HEAD --output dev/exports/releases/current
python3 dev/scripts/verify-production.py --manifest dev/exports/releases/current/release.json
```

On a deployment host, install `dev/scripts/post-receive` as the bare repository's executable `hooks/post-receive`. Configure `relu.webRoot` and `relu.backupRoot` in that repository's Git config with absolute, separate directories. The hook deploys `main`, serializes updates with `flock`, and records the exact commit in the private backup root's `current-release.json`. Push the verified commit to GitHub, wait for release checks, and then push the same commit to the deployment remote. Compare both remote refs and the deployment receipt before considering a release complete.

The deployer's explicit `rollback` mode restores a selected backup's prior files. Use the same web/backup roots and check for later unrelated changes before restoring. It leaves newly added files in place, unlinked by restored pages.

Local databases, Python bytecode, training candidates, generated bot-pack experiments, archives, and host-specific release reports are ignored. Runtime databases are created by the PHP endpoint when needed and are never part of a public source release. The frozen policy evaluation is published in `data/policy-evaluation.json`, numerical fixtures live in `tests/fixtures/`, and source data/baselines remain versioned for reproducibility.
