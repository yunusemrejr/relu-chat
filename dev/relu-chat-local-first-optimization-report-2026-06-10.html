2. Current System Map

ReLU.chat is a static, browser-only chatbot platform. There is no backend in the conversation path. The browser loads bot-specific KB files and shared engine modules, computes embeddings locally, ranks fragments locally, plans the response with a small local MLP policy, and renders text with local KaTeX.

Strong Current Design Choices

  • Static hosting and no server-side inference: the privacy story is simple and defensible.
  • Local model files under assets/models/ with env.allowRemoteModels = false.
  • Progressive BOW bootstrap lets early turns happen before MiniLM finishes loading.
  • BM25 and dense ranking are fused before policy planning.
  • The policy contract is explicit through AnswerPlan validation.
  • Session memory tracks history, recent entities, fragment usage, ambiguity, engagement, and an EMA query vector.
  • Service worker already handles model caching and Range requests.

Current Gaps To Treat As Product Opportunities

  • Follow-up type drift: how? and why? are currently collapsed to elaborate in one path.
  • Seeded composition is only partially wired. Math.random() and unseeded pick() remain in shared and legacy paths.
  • Legacy chat/*/js/nlp.js files are still present even though current chat wrappers import core/chatbot-engine.js.
  • Knowledge, fragment metadata, policy weights, and config are split across several shapes instead of a single bot-pack manifest.
  • Policy accuracy is not yet strong enough for high-confidence claims about intent choice.
  • Answer length is mostly a side effect of fragment count rather than an explicit budget chosen by policy.
  • There is no safe diagram AST, no diagram metadata in fragments, and no renderer contract for visual answers.
  • MiniLM and ONNX Runtime loading still dominate cold-start time, especially on mobile.

4. Algorithm Optimizations

4.1 Retrieval: Replace O(N*k) BM25 Top-K With An Inverted Index

Current BM25Scorer.scoreTopK() performs repeated scans to find the best unused document. That is acceptable for 38 to 77 topics, but it recomputes scores repeatedly and will become wasteful when KBs grow or when fragments become independently searchable.

CurrentReplacementBenefit
Compute score for each doc repeatedly while selecting top K. Build term -> posting list at pack time; score only docs touched by query terms. For sparse queries, ranking cost becomes proportional to matching postings, not all documents.
Name/alias boosting through text repetition. Store field weights explicitly: title 4.0, alias 3.0, summary 1.5, fragment 1.0. Cleaner ranking, no inflated doc length side effects.
Bigram bonus checked against doc bigram set. Index bigrams as postings with lower weight. Consistent phrase scoring with no per-doc set allocation. 
Proposed pack-time index:
{
  "terms": {
    "nash": [[entryId, tfTitle, tfAlias, tfBody], ...],
    "nash_equilibrium": [[entryId, tfPhrase], ...]
  },
  "idf": { "nash": 1.92, "nash_equilibrium": 2.43 },
  "docLen": [...],
  "avgDocLen": 123.4
}

4.2 Entity Extraction: Alias Regex To Automaton + BK-Tree

compileAliasRegex() precompiles regexes per entry and extractEntities() loops through the KB. This is workable now, but adding bots, synonyms, and multilingual variants will increase cost and ambiguity.

  • Build an Aho-Corasick or FlashText-style alias automaton at pack time for exact multi-token aliases.
  • Keep a small BK-tree or SymSpell table for typo correction over aliases.
  • Normalize accents, punctuation, Greek letters, formula tokens, and hyphen variants in one tokenizer.
  • Emit entity candidates with spans and scores: {kbId, spanStart, spanEnd, alias, score, method}.
  • Resolve overlapping aliases with longest-span-first plus graph centrality.

4.3 Dense Retrieval: Precompute And Pack Entry/Fragment Embeddings

On first dense load, the runtime encodes the KB in batches after MiniLM loads. That is a good progressive step, but it still burns CPU on every first visit per bot. For static KBs, entry and fragment vectors should be generated offline and shipped in the bot pack.

Vector TypeCurrentRecommended
Entry embeddingsComputed in browser after model load.Ship Float16 or Int8 normalized vectors per bot.
Fragment embeddingsComputed lazily through embedCached().Pack fragment vectors, then use query-only embedding at runtime.
Domain prototypesEmbedded at init if configured.Pack domain prototype vectors with versioned model hash.
CompressionJSON + ONNX assets.Use binary .bin vectors with header: magic, modelHash, dim, dtype, count.

This keeps all inference local while reducing first dense-ready time. The browser still embeds the user query locally, but does not re-embed static KB text.

4.4 Ranking Fusion: Move From Fixed Weighted Sum To RRF + Learned Ranker

The current ensemble uses dense 0.7 and sparse 0.3 plus a simple rerank. Better local ranking can be achieved with:

  • Reciprocal Rank Fusion (RRF) as a robust default when sparse and dense score scales disagree.
  • A tiny learning-to-rank MLP or logistic calibrator over features: dense sim, BM25, entity hit, title hit, follow-up boost, fragment freshness.
  • MMR for diversity: choose high-scoring topics while penalizing near-duplicates.
  • Topic graph expansion after top-1 only when confidence is high or the user asks "what else".
  • Confidence thresholds calibrated per bot, not globally copied across all bot configs.

4.5 Fragment Selection: Use Metadata And Diversity Earlier

Fragment selection currently embeds and softmaxes candidate fragments with a recent-fragment penalty. Stronger selection should combine:

  • Semantic match: query/fragment cosine.
  • Answer budget: short mode picks one high-density fragment; long mode picks def + int + ex + app/form.
  • Difficulty fit: user asks "simple" -> lower difficulty; "prove" -> formal and higher difficulty.
  • Freshness: penalize exact fragment repetition and semantically similar paraphrase repetition.
  • Truth/source confidence: prefer high-confidence fragments when challenged or asked for evidence.
  • Diagram availability: if a concept has a visual template and the user would benefit, reserve room for it.

4.6 Query Understanding: Local Expansion Without LLMs

ReLU.chat can become more intelligent without a cloud LLM by adding deterministic local understanding layers:

  • Per-bot synonym maps built from aliases and related concepts.
  • Local spelling correction against alias vocabulary.
  • Question operator classification: what, why, how, when, compare, example, prove, summarize, challenge.
  • Formula/token recognizers for game matrices, probability notation, ML metric names, and historical date ranges.
  • Graph-aware expansion: if top topic is "Nash equilibrium" and intent is example, include "Prisoner's Dilemma" only when helpful.
  • Contradiction/rejection detection: "not that", "I meant X", "wrong topic", "no just X".

5. Conversation Awareness

5.1 Fix The Verified Follow-Up Bug

Observed failure: dev/benchmarks/test-followup.js expects how? -> how and why? -> why, but the current simple detector returns elaborate in three assertions. The feature extractor and MLP support distinct codes 9 and 10, so the lost nuance is in session detection precedence.

Recommended fix:

  • Change singleWordMap.how to how and singleWordMap.why to why.
  • Move short phrase patterns for why and how before generic more/elaborate patterns.
  • Add test cases for punctuation variants: how?, how, how so?, why?, why so?.
  • Confirm MLP decision path uses followup:override-how and followup:override-why.

5.2 Session Memory Should Become A Structured Local State Machine

SessionMemory already tracks turns, entities, fragments, ambiguity, summaries, engagement signals, and an EMA embedding. The next step is to make this state explicit and queryable by policy and renderer. 

{
  "turn": 12,
  "activeTopic": "nash_eq",
  "topicStack": ["nash_eq", "prisoners_dilemma"],
  "lastIntent": "example",
  "userDepthPreference": "medium",
  "diagramPreference": "auto",
  "activeEntities": [{"id":"nash_eq","weight":0.91}],
  "recentFragments": ["nash_eq:def", "nash_eq:int"],
  "unresolvedClarification": null,
  "localFeedback": {"shortAnswers": 3, "diagramsOpened": 2}
}

All of this should remain in memory by default. If persistence is enabled, store it in IndexedDB behind a local-only profile switch and provide a "clear local learning" action.

5.3 Wire The EMA Summary Vector Into Real Features

The session currently maintains getSummaryEmbedding(), but the policy feature contract does not yet include it directly. Instead of expanding the 25-feature vector immediately, add derived scalar features first:

  • queryToSessionSim: cosine of current query to EMA vector.
  • sessionTopicStability: how stable recent top topics are.
  • fragmentNoveltyPressure: fraction of candidate fragments recently used.
  • engagementDepth: rolling measure from deepening/challenging/clarifying signals.
  • answerBudgetPreference: local profile or inferred short/medium/long preference.

If keeping exactly 25 features is important for current weights, create policy v0.5 with versioned feature schema rather than silently changing the vector.

5.4 Clarification Should Be An Answer Mode, Not Just A Fallback

The action schema already has mode: clarify. Use it more aggressively when:

  • Dense and sparse disagree strongly and no entity is found.
  • Top two topics are close and the user query is short.
  • The user uses pronouns without a stable previous topic.
  • A correction target cannot be matched with high confidence.

Clarification should be concise, with 2 to 4 local options, and should update session state so the next answer resolves the pending ambiguity.

6. Answer Variation And Length Control

The current system varies answers through fragment choice, connectors, openers, closers, and policy-selected fragment counts. The user request needs a more explicit automatic length and variation system.

6.1 Add Answer Budget To AnswerPlan

BudgetPolicy MeaningRenderer Contract
microGreeting, quick correction, direct definition.1 fragment, no related topics, no closer unless useful.
shortUser asks quick/simple, mobile, low confidence, or repeated topic.1 to 2 fragments, max 80 words, optional tiny diagram.
mediumDefault for most desktop and first educational answers.2 to 3 fragments, max 170 words, one related topic.
longUser asks deep, formal, evidence, or "tell me more".3 to 5 fragments, sectioned answer, example or formula.
diagram_plus_textConcept has a strong visual representation.Text plus safe SVG/HTML diagram AST.

6.2 Infer Budget Locally

  • Lexical cues: "brief", "tl;dr", "short", "summary" -> short.
  • Depth cues: "prove", "derive", "why", "how exactly", "detailed" -> long.
  • Device hints: small screen, low memory, or Save-Data -> start short unless user asks deep.
  • Conversation state: if user repeatedly asks follow-ups, increase detail gradually.
  • Local feedback: thumbs up on short answers raises prior for short answers on that device.
  • Uncertainty: low confidence should trigger clarify or short answer with "I may be reading this as...".

6.3 Deterministic Variation

Variation should be reproducible for the same local state so tests and user experience are stable. Use a seed based on bot id, KB version, normalized query, selected topics, turn number, answer budget, and creativity bucket. 

seed = hash32(botId + kbVersion + normalizedQuery + topics.join(",") + turn + budget + creativityBucket)
setCompositionSeed(seed)
renderer picks opener, connectors, examples, and closers from seeded RNG only

This also lets the user request "another version" by incrementing a local variant counter without changing the semantic plan.

7. Visual SVG/HTML Diagram Layer

The safest way to add visual answers is not to let fragments contain raw HTML. Instead, add a diagram AST schema that the renderer turns into DOM/SVG nodes. This keeps everything local, inspectable, and XSS-resistant.

7.1 Diagram Types To Add First

BotDiagram TypeExamplesWhy It Helps
Game theory 2x2 payoff matrix, extensive-form tree, equilibrium marker, auction flow. Prisoner's Dilemma, Chicken, Stag Hunt, Nash equilibrium, minimax. Game theory is inherently visual; a matrix often explains faster than paragraphs.
Data science Confusion matrix, bias-variance curve, train/test split bar, pipeline DAG, decision tree. Precision/recall, cross-validation, leakage, PCA, ensembles. Many ML concepts are process or matrix concepts; diagrams reduce cognitive load.
Golden Age Timeline, scholar influence graph, invention flow, map-lite schematic. House of Wisdom, translation movement, optics, algebra, astronomy. Historical relationships are easier to understand with chronology and influence.

7.2 Diagram AST Example

{
  "type": "payoff_matrix",
  "title": "Prisoner's Dilemma",
  "players": ["Player 1", "Player 2"],
  "rows": ["Cooperate", "Defect"],
  "cols": ["Cooperate", "Defect"],
  "cells": [
    {"payoff": [3,3], "label": "mutual cooperation"},
    {"payoff": [0,5], "label": "P1 exploited"},
    {"payoff": [5,0], "label": "P2 exploited"},
    {"payoff": [1,1], "label": "Nash equilibrium", "highlight": true}
  ],
  "caption": "Defect/defect is stable even though cooperate/cooperate is better for both."
}

7.3 Renderer Safety Rules

  • Never inject raw diagram HTML from KB strings.
  • Use typed AST objects validated against a JSON schema.
  • Create SVG nodes with document.createElementNS and text nodes with textContent.
  • Allow only known style tokens: color roles, emphasis, highlight, muted.
  • Render responsively: diagrams must fit within chat width on mobile and support horizontal scroll only for wide matrices.
  • Cache rendered diagram AST by fragment id and theme.
  • For accessibility, include title, caption, and text table fallback.

7.4 Policy Integration

Add new fields to AnswerPlan:

{
  "visualMode": "none | inline | card | expandable",
  "visualType": "payoff_matrix | tree | timeline | flow | chart",
  "visualRef": "fragment-or-topic-diagram-id",
  "visualPlacement": "before_text | after_intro | after_text",
  "visualBudget": "tiny | standard | detailed"
}

The policy should choose visuals when a diagram is available, confidence is high, and the answer budget permits it. Mobile can default to expandable; desktop can render inline.

8. RL And Policy Pipeline Improvements

8.1 Current Policy State

  • The runtime policy is a local pure-JS MLP with 25 inputs, 128 and 64 hidden units, and six action heads.
  • The shipped runtime manifest is version 0.4.0 and the active JSON weights file is about 362 KB.
  • A 43-byte policy WASM exists as a stub-like artifact; the JS MLP is the real practical path today.
  • Policy dev tests pass, but the 10-scenario benchmark reports only 30% intent accuracy.
  • Training scripts include both a broad train-policy.py pipeline and a newer train_real.py pipeline with anti-collapse measures.

8.2 Make Training One Reproducible Pipeline

Merge the useful parts of train-policy.py and train_real.py into a single command that produces a signed artifact directory:

  config.json
  dataset-summary.json
  train-metrics.jsonl
  validation-report.json
  confusion-matrix.json
  policy.weights.json
  policy.weights.bin

The manifest should include feature schema version, reward weights, dataset hash, KB hash, model hash, and evaluation scores. Runtime should refuse mismatched feature schemas.

8.4 Add Offline Golden Tests

Create a per-bot golden set with at least these buckets:

  • Direct definitions for every topic alias.
  • Examples for every topic that has example fragments.
  • Formal questions for formula-heavy topics.
  • Application questions for practical topics.
  • Comparison pairs from related topic graph.
  • Short follow-ups: how, why, example, simplify, summarize, what else, prove it, compare.
  • Topic corrections and rejections.
  • Off-topic and ambiguous queries.
  • Mobile style queries: terse, typo-heavy, punctuation-only.

A policy build should fail if mode, intent, topic, or answer budget regression exceeds a threshold. This matters more than total reward curves.

8.5 Do Not Over-Optimize The Tiny MLP First

The policy model is about 13K parameters. Optimizing the MLP into WASM is not the top performance opportunity compared with MiniLM, ONNX Runtime, KB encoding, and main-thread scheduling. Prioritize model/asset loading and retrieval packaging first.

9.2 Workerized Load Plan

The chat UI should become usable immediately and never freeze. Recommended sequence:

  1. Main thread renders chat shell, suggestions, local cached history, and input.
  2. Worker loads bot pack and sparse indexes.
  3. Worker returns basic_ready: BOW/BM25 answers available.
  4. Worker loads policy JSON/bin and returns policy_ready.
  5. Worker loads MiniLM/ONNX runtime when needed and returns progress events.
  6. Worker hot-swaps dense vectors and returns dense_ready.
  7. All later query requests use worker messages with cancel tokens.

9.3 Mobile-Specific Rules

  • If navigator.connection.saveData is true, default to sparse/BOW mode until the user asks for richer answers.
  • If navigator.deviceMemory is low, avoid caching all fragment embeddings and diagrams at once.
  • Use short answer budget by default on narrow screens unless the query asks for depth.
  • Make large diagrams expandable with a text fallback and no layout shift.
  • Do not preload the 22.97 MB model on the landing page; wait for chat page or explicit install/warm-up.
  • Throttle background model preloads while the tab is hidden or battery saver is active.

9.4 Service Worker Improvements

  • Use a manifest-driven cache list from bot packs instead of hardcoded model paths.
  • Separate app shell cache, bot pack cache, model cache, and generated local user data.
  • Add cache size accounting and a "clear model cache" UI action.
  • Use stale-while-revalidate for code, cache-first for versioned bot packs and model files.
  • Cache only one ONNX Runtime variant after feature detection.
  • Include policy and bot-pack manifest hashes in cache keys to avoid stale weights.

10. Local-Only Data Model

The user requirement is clear: make the system smarter while keeping all data locally in the user's browser. That is feasible if personalization is implemented as optional local state and never syncs.

10.2 Local Adaptation Without Retraining

  • Adjust answer budget priors from local feedback.
  • Boost fragments the user expanded or marked useful.
  • Penalize fragments the user downvoted, only on the same device.
  • Remember that the user prefers diagrams for a bot or topic.
  • Prefer simpler fragments if the user often asks "simpler".
  • Keep an on-device "local profile vector" of preferences, not raw sensitive transcripts.

10.3 Local-Only UX Requirements

  • Settings panel: "Local learning: on/off", "Clear local chat memory", "Clear downloaded models".
  • Per-chat banner: "This preference is stored only in this browser."
  • Export local profile as JSON for user-controlled backup.
  • Do not add telemetry endpoints or remote feedback calls.
  • Tests should assert no external network URLs are used for model or feedback data.

The current test footprint is solid for helpers and schemas. The next step is behavior and performance proof.

12.1 Tests To Add
